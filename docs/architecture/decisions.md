# Architectural decisions

Each significant decision is recorded as an ADR in [`docs/decisions/`](../decisions/). Summary:

| ADR | Decision | Key trade-off |
|-----|----------|---------------|
| [0001](../decisions/0001-separate-core-process.md) | Orchestration lives in a separate, long-running `switchyard-core` process; the desktop is a client that can launch it but never owns it. | Two binaries and a protocol to version, in exchange for agent sessions that survive the UI. |
| [0002](../decisions/0002-unix-socket-json-lines.md) | IPC over a `0600` Unix domain socket with peer-UID check; newline-delimited JSON frames; versioned `initialize` handshake. | Simple and inspectable; macOS/Linux only until a named-pipe transport exists. |
| [0003](../decisions/0003-sqlite-persistence.md) | SQLite (bundled) in WAL mode, `synchronous=FULL`, a single writer connection, migrations embedded and tracked with `user_version`. | One fsync per commit; trivial ordering and no pool. |
| [0004](../decisions/0004-event-engine.md) | Persist-then-publish; transactional outbox (`publish_with`); total order by `seq`; bounded broadcast with lossless catch-up from the journal. | Durable events cost an fsync; high-rate agent output may need a separate channel later. |
| [0005](../decisions/0005-git-cli.md) | Inspect repositories through the `git` CLI (`--porcelain=v2`, no optional locks, no prompts, timeouts). | Requires `git` installed; matches exactly what agents see. |
| [0006](../decisions/0006-crate-layout.md) | No empty `agents`/`permissions` crates; `switchyard-git` instead of `switchyard-workspaces` for now; a separate `switchyard-client`; per-crate integration tests. | Deviates from the initial proposal for concrete reasons. |
| [0008](../decisions/0008-claude-code-stream-json.md) | Claude Code runs as one long-lived `claude -p` process per session, with stream-json on stdin and stdout; permission prompts arrive as `can_use_tool` control requests over stdio. | Relies on control messages that are verified but undocumented for the CLI; pinned by fixtures and a fake CLI. |
| [0009](../decisions/0009-durable-vs-live-output.md) | Durable journal for agent activity; a lossy, bounded live channel for token streams, with an in-progress snapshot for reconnecting clients. | Fragments streamed while disconnected are not replayed. |
| [0010](../decisions/0010-agent-process-ownership.md) | Agents are children of Core only. Graceful shutdown stops them. After a crash the process is not re-adopted: the session is marked `failed` and must be resumed explicitly. | No hot recovery after a Core crash. |
| [0011](../decisions/0011-agent-workspace-boundary.md) | `--restricted`, `--strict-mcp-config`, an explicit tool list, and an `ask` rule for every enabled tool (Bash only until [0017](../decisions/0017-normalized-operations.md)), so every request reaches Switchyard's policy evaluation. | No OS-level sandbox is claimed. |
| [0012](../decisions/0012-project-workspace-session.md) | Project (registered repo) → workspaces (Core-owned worktrees) → sessions; one live session per workspace, many per project; `sessions.start` requires a workspace; M2 checkout records become `legacy_checkout`. | One documented incompatible change inside protocol v1. |
| [0013](../decisions/0013-worktree-location-and-branches.md) | Worktrees in `<data dir>/workspaces/<project>/<workspace>`, branch `switchyard/<workspace-id>`, identity verified before every use, branches never reused. | Moving the repository breaks the links until it is moved back or repaired. |
| [0014](../decisions/0014-workspace-recovery-and-cleanup.md) | Nothing is deleted automatically; cleanup is archive → checked report → confirmation bound to the inspected state → `git worktree remove` without force; branches kept; reconciliation only changes statuses. | Disk use grows until the operator cleans up. |
| [0015](../decisions/0015-protocol-version-2.md) | Protocol 2 with minimum 2 on both sides; old clients and old Cores are refused during `initialize` with actionable, structured errors. | A running old Core must be stopped during upgrades. |
| [0016](../decisions/0016-approval-policy-model.md) | Approval policies: system restrictions, then the most restrictive matching rule (deny > ask > allow), then built-in defaults, then caps that turn `allow` into `ask`; project and workspace scopes; global revisions; protocol 3. | A broad `ask` makes narrower `allow` rules ineffective; no session scope or global rules. |
| [0017](../decisions/0017-normalized-operations.md) | Every Claude tool goes through Switchyard (`ask` rules for all enabled tools); requests are classified into adapter-neutral operations; Bash is always `shell`; unknown, disabled and malformed requests are denied. | One evaluation and event per read; a new CLI field turns allows into asks until it is classified. |
| [0018](../decisions/0018-policies-and-human-approvals.md) | One evaluation path for every request, recorded before answering; human decisions never become rules; pending approvals stay bound to their evaluation and can only be denied by later changes. | An operator who just allowed something still has to decide requests that were already pending. |
| [0019](../decisions/0019-policy-threat-model.md) | Policies are authorization and workflow, not a sandbox; the protections and the non-protections are listed. | Allowed commands keep the user's full privileges. |
| [0020](../decisions/0020-codex-app-server-adapter.md) | Codex through its native `codex app-server` over stdio, stable API only; one process and one thread per session; Codex assigns the thread id; a failed resume fails the session, never a new thread. | Tied to an app-server the CLI marks experimental; verified against 0.166.0 only. |
| [0021](../decisions/0021-codex-permission-mediation.md) | Codex threads use `approvalPolicy: "untrusted"` and `sandbox: "workspace-write"`; tools that act without approval are disabled; commands are always `shell`, patches map by change kind; mixed patches, moves and sub-agent requests are denied; allow = `accept`, deny = `decline`. | Every Codex read asks by default; an approved operation can run outside Codex's sandbox. |
| [0022](../decisions/0022-agent-capabilities-and-protocol-4.md) | Capabilities are `supported`/`unsupported`/`unknown`, `supported` only when verified; protocol 4 with minimum 4. | Older desktops are refused. |
| [0023](../decisions/0023-tasks-independent-of-sessions.md) | Tasks are durable and independent of sessions; an assignment gives one role to one provider in one workspace; Core follows sessions through the journal with an idempotent, replayable reaction; only the operator completes. Protocol stays 4 (additive). | One task per workspace at a time. |
| [0024](../decisions/0024-task-dependencies.md) | Dependencies are an acyclic, same-project graph checked on every change; readiness is derived; only Core's own dependency blocks lift automatically. | Dependencies are fixed once work starts. |
| [0025](../decisions/0025-task-messages-reports-and-context.md) | A versioned task context in the first message; agents answer with a fenced `switchyard-report` JSON block, parsed with limits and a per-role allowlist into structured messages; a message never authorizes anything. | A report after more than 8 KiB of final text is lost; agents can ignore the format. |
| [0026](../decisions/0026-controlled-delegation.md) | Agents only propose subtasks; the operator approves each one into a draft. | No automatic decomposition. |
| [0027](../decisions/0027-review-sessions.md) | Review sessions: file changes denied by the system policy, commands always ask, workspace fingerprinted before and after; a change forces the verdict to `blocked`. | Approved commands still run with the user's permissions. |
| [0028](../decisions/0028-integrations-separate-from-tasks.md) | Integrations are their own record bound to exact commits, with blockers computed from Git; task states unchanged; delivery is not completion; the workspace is `integrating` while Core works in it. | A completed task cannot be re-reviewed for a changed source. |
| [0029](../decisions/0029-git-strategy-and-commit-binding.md) | Always a merge commit of the approved target and source; the source must contain the target (update in the workspace; conflicts resolved there); compare-and-swap ref update or fast-forward of a clean checkout; approvals and reviews bound to exact commits/trees; hooks disabled. | Repository hooks do not run for Switchyard's merges. |
| [0030](../decisions/0030-validation-execution.md) | Validation commands are argv, evaluated by the M4 policy (ask needs the operator), bound to the source commit, run in process groups with timeouts, cancellation and 64 KiB output tails. | Commands inherit Core's environment. |
| [0031](../decisions/0031-integration-recovery-and-audit.md) | The merge commit is recorded before the branch moves; recovery settles from the target branch; every step is journaled and the merge commit carries trailers. | Only the ref update is atomic. |
| [0032](../decisions/0032-core-owned-integration-operations.md) | Git-changing integration steps are Core-owned operations: durable, supervised, one per integration, not cancelled by a client disconnect; bounded wait at shutdown; settled from Git after a restart. | A killed Core can still leave a checkout partially updated; that is reported, not repaired. |
| [0033](../decisions/0033-workflow-orchestration.md) | Built-in `engineering@1` workflow: a pure decision function drives investigation → implementation → review → bounded corrections → the delivery gate, creating assignments itself (unique step keys, one transaction per decision); provider + model per role from project settings with task overrides, snapshotted; model choices read from the installed CLIs. | Sequential only; no stage timeouts or provider fallback yet. |
| [0035](../decisions/0035-agent-organizations.md) | Agent organizations: agents (tree, no fixed depth), organization tasks backed by M6 tasks, and the runtime kept apart; supervisors' `switchyard-org` directives applied atomically by Core within the project's limits; subtasks created through proposals decided by Core; Core-verified evidence and labelled shared context; provider-neutral selection from verified capabilities and the user's estimates; delivery through M7 behind a review gate. | Supersedes ADR 0026 inside organizations only. |
| [0036](../decisions/0036-organization-supervision-and-runtime.md) | One session at a time per organization; event-driven supervision checkpoints; Core interrupts work that leaves its scope; instructions reach the next turn (no mid-turn steering); restarts wait for the user. | Sequential until per-branch workspaces exist. |
| [0037](../decisions/0037-policy-auto-mode.md) | Per-project auto mode: with no matching rule, file changes and any foreground shell command inside the workspace are allowed (`reason: auto_mode`); rules, system denials, caps (outside paths, `.git`, background, unknown fields) and review sessions still apply; versioned and journaled on the global policy revision. | Fewer interruptions for commands whose effects are not confined to the workspace. |
| [0038](../decisions/0038-review-triage.md) | `engineering@2`: review findings go to reasoning, which decides `fix` (implementation) or `dispute` (back to review, implementation skipped); no separate correction role. | One more agent turn per round with findings. |
| [0039](../decisions/0039-workflow-test-gate.md) | Core runs the implementer's named unit/integration/regression (and, for UI changes, browser) tests through the policy before every review; failures go to reasoning; results are verified evidence. | Test commands come from agents, so they run only as the policy allows or the operator authorizes. |
| [0040](../decisions/0040-workflow-subtasks.md) | Reasoning's first plan of 2–8 subtasks becomes the workflow's plan; each runs the loop in turn; the task is delivered once. | Supersedes ADR 0026 for that plan only; sequential. |
| [0034](../decisions/0034-workflow-delivery.md) | The workflow delivers through M7: an approved review prepares the task's integration, validation of policy-allowed commands starts by itself, the operator commits, authorizes `ask` commands and approves the exact commits; after `integrated` the workflow is `delivered` and the task completed. Delivery state is derived from the integration record. | The commit stays a manual click (ADR 0029). |
| [0007](../decisions/0007-toolchain-and-versions.md) | Tauri 2.12 (not 3-alpha), Rust 1.99.1 pinned, React 19.3, Vite 8, TS 5.9. | Conservative TypeScript choice. |

## Decisions deliberately deferred

- **How Core is started at login** (LaunchAgent vs. on-demand from the desktop). It is currently on
  demand only.
- **Remote delivery** (push, pull requests, hosting integrations). M7 integrates locally only.
- **OS-level sandboxing** of agent commands. Worktrees isolate source trees only.
- **Global (cross-project) policy rules, session-scoped rules and "always allow" shortcuts.**
  Milestone 4 has project and workspace rules only (ADR 0016); ADR 0037 adds a per-project auto mode.
