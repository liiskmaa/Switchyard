# Codex integration (milestone 5)

Switchyard drives the user's installed OpenAI Codex CLI through its native **app-server** interface,
alongside Claude Code. This document records what was verified against the real CLI, how the adapter
fits Switchyard's shared agent architecture, and where Codex differs from Claude.

Verified against **`codex-cli 0.166.0`** (macOS, ChatGPT sign-in), using:

- `codex --help`, `codex app-server --help`, `codex features list`;
- the protocol schema generated by the installed binary (`codex app-server generate-json-schema` and
  `generate-ts`), which the official documentation names as the exact contract for that version;
- the official app-server documentation (developers.openai.com/codex/app-server, served from
  learn.chatgpt.com/docs/app-server) and `codex-rs/app-server/README.md` in the openai/codex
  repository;
- recorded sessions against the real CLI in a throwaway repository (see "Verification" below).

## Interface selection

| Option | Verdict |
|---|---|
| `codex app-server` over stdio | **Selected.** Documented, the interface Codex's own IDE extension uses, long-lived and multi-turn, with server-initiated approval requests. |
| `codex exec` | Rejected. One-shot and non-interactive: no multi-turn session in one process, no approval round-trip to a client. |
| `codex app-server --listen unix://…` / `ws://…` | Rejected. WebSocket transport is documented as experimental and unsupported; stdio needs no listener and no authentication. |
| `codex app-server daemon` / `proxy` | Rejected. A shared per-user daemon would put Switchyard sessions in a process Switchyard does not own or supervise. |

The `app-server` command is labelled `[experimental]` in `codex --help`; its stable surface (the
methods used here, with `experimentalApi` left off) is what the documentation describes. Switchyard
does not opt into the experimental API. Because the protocol is versioned only by the CLI release,
the adapter records the version it was verified against and reports any other version as untested.

## Transport and framing

- One `codex app-server` child per Switchyard session, launched directly (no shell) with
  `--listen stdio://`, stdin/stdout piped, stderr captured into a bounded tail buffer.
- JSON-RPC 2.0 messages without the `"jsonrpc"` field, one JSON object per line.
- Three message kinds: client requests (we send `id` + `method`), server notifications (`method`,
  no `id`) and **server requests** (`id` + `method`, which we must answer).

## Process lifecycle

1. **Spawn** `codex app-server --listen stdio://` with the hardening flags below, cwd = the workspace,
   environment filtered by an allow-list.
2. **Handshake**: `initialize {clientInfo: {name: "switchyard", …}}` → response; then the
   `initialized` notification. Switchyard never calls `account/read` (it returns the account email).
3. **Thread**: `thread/start` (new session) or `thread/resume {threadId}` (resume), both with
   `cwd`, `approvalPolicy: "untrusted"` and `sandbox: "workspace-write"`. The thread id becomes the
   session's native id. A failed resume (e.g. "no rollout found") ends the process and fails the
   session; Switchyard never starts a new thread in its place.
4. **Turns**: `turn/start {threadId, input: [{type: "text", text}]}`; notifications stream until
   `turn/completed`. Messages sent while a turn runs are held by the adapter and start the next turn
   when the current one completes (Codex's own `turn/steer` alters the running turn and is not used).
5. **Interrupt**: `turn/interrupt {threadId, turnId}`; the turn completes with status `interrupted`.
6. **Stop**: close stdin (Codex exits in ~0.1 s), then SIGTERM, then SIGKILL after the configured
   grace periods. The child runs in its own process group with `kill_on_drop`.
7. **Core shutdown / restart**: identical to Claude. Pending approvals are cancelled and answered,
   processes are stopped, and sessions found live on start-up are marked failed. Nothing is restarted
   automatically.

### Hardening flags

Passed on the command line for every Switchyard-launched app-server:

```
--disable apps --disable plugins --disable remote_plugin --disable multi_agent
--disable browser_use --disable browser_use_external --disable computer_use
--disable in_app_browser --disable image_generation --disable hooks --disable goals
-c web_search="disabled" -c mcp_servers={}
```

These remove tools that could act **without** an approval request: MCP servers and plugins
(including those configured in the user's `~/.codex/config.toml`), web search, browser and computer
use, image generation and user hooks. Verified: with them, web search is unavailable and no MCP
tools are listed.

## Session and turn model

| Switchyard | Codex |
|---|---|
| Session | One app-server process + one thread |
| Native session id | Thread id (assigned by Codex at `thread/start`, UUIDv7) |
| Turn | Turn (`turn/start` … `turn/completed`) |
| Resume | New process + `thread/resume {threadId}` (verified: context is restored) |
| Interrupt | `turn/interrupt` |
| Queue during a turn | Held by the adapter, started after `turn/completed` |

Codex stores threads in the user's Codex home (`~/.codex`), as Claude stores sessions in `~/.claude`.
Switchyard does not use a separate `CODEX_HOME`, because the user's sign-in lives there.

## Event mapping

| Codex message | Switchyard |
|---|---|
| `thread/start` / `thread/resume` result | `agent.ready` (thread id, model) |
| `turn/started` | (state already `running`) |
| `item/started` `agentMessage` | live `message_start` |
| `item/agentMessage/delta` | live text (never journaled) |
| `item/reasoning/summaryTextDelta` | live thinking (never journaled) |
| `item/completed` `agentMessage` | `agent.message` + live `message_stop` |
| `item/started` `commandExecution` | `agent.tool_started` (tool `shell`, input `{command, cwd}`) |
| `item/completed` `commandExecution` | `agent.tool_completed` / `agent.tool_failed` (`declined` → rejected) |
| `item/started` `fileChange` | `agent.tool_started` (tool `apply_patch`, input: paths and kinds) |
| `item/completed` `fileChange` | `agent.tool_completed` / `agent.tool_failed` |
| other item types (`mcpToolCall`, `webSearch`, `collabAgentToolCall`, …) | `agent.tool_started` / finished, plus an `agent.warning` that Switchyard did not mediate it |
| `thread/tokenUsage/updated` | kept; reported on `agent.turn_completed` as `usage` |
| `turn/completed` | `agent.turn_completed` (`completed`, `interrupted` or `failed` with the error message) |
| `turn/interrupt` response | `agent.interrupted` |
| `error` (`willRetry: false`), `warning`, `configWarning` | `agent.warning` |
| item requests: command / file-change approval | permission request → policy evaluation |
| `serverRequest/resolved` for an unanswered request | permission cancelled (approval settled `cancelled`) |
| `thread/status/changed`, `turn/diff/updated`, `turn/plan/updated`, `account/*`, `mcpServer/*`, `remoteControl/*`, reasoning items | ignored (not user-facing activity) |

Only notifications for the session's own thread are processed. Codex can run sub-agent threads on
the same connection; their notifications are ignored and their approval requests are denied.

## Permission and approval flow

### Codex's native model (verified)

- `approvalPolicy: "untrusted"` makes Codex ask **before every command and every patch**. Verified with
  `pwd`, `ls`, `echo`, `git status`, `rg`, `cat` and `touch`: each produced an approval request; nothing
  ran unasked. Patches (`apply_patch`) produce `item/fileChange/requestApproval`.
- The unit of approval is one command execution or one patch (which may touch several files).
- Decisions: `accept`, `acceptForSession`, `decline`, `cancel` (plus exec-policy and network-policy
  amendments for commands). `decline` refuses that operation and the turn continues; `cancel` also
  interrupts the turn. Codex does not pass a reason to the model, only that the user rejected it.
- If the client never answers, Codex waits. On `turn/interrupt`, Codex ends the turn and reports the
  pending request as resolved (`serverRequest/resolved`).
- File-change requests carry no paths: the paths and change kinds come from the `fileChange` item
  announced just before the request (`item/started`), matched by `itemId`.

### Switchyard's mapping

Every approval request goes through the single central path:
adapter request → Codex classifier → path facts → `policy::evaluate_in_tx` (committed) → decision.

| Codex request | Normalized operation |
|---|---|
| `item/commandExecution/requestApproval`, `kind: "command"` | `shell`; command = the script run by the shell (`/bin/zsh -lc '<script>'` is unwrapped only when it is exactly that form). A `cwd` other than the session's working directory is flagged, so the request is never allowed automatically. |
| same, with `networkApprovalContext` | `network` (denied by default) |
| same, any other `kind` (stdin, human command, …) | `unknown` (denied) |
| `item/fileChange/requestApproval` | all `add` → `file_write`; all `update` → `file_edit`; all `delete` → `file_delete`; paths from the matching item. A patch that mixes kinds, moves a file, or whose item was not seen is **unclassified and denied** (Codex is told to retry with separate patches). `grantRoot` is flagged (never allowed automatically, and never granted). |
| `item/permissions/requestApproval`, `mcpServer/elicitation/request`, `item/tool/requestUserInput`, `item/tool/call`, any other server request | `unknown` (denied; answered with an empty grant, `decline`, or a JSON-RPC error as the method requires) |
| request from a thread other than the session's | unclassified (denied) |

Answers: **allow → `accept`** (never `acceptForSession` or an amendment, so no approval outlives the
request); **deny → `decline`**. Expiry, cancellation, agent exit and Core shutdown deny unresolved
requests exactly as for Claude; duplicate decisions are rejected by the `pending → final` SQL guard
before anything is sent.

Reads are not a separate tool in Codex: it reads files with shell commands (`cat`, `rg`, `sed`).
Switchyard does **not** trust Codex's parsed `commandActions` to downgrade those to `file_read`,
because the executed text is an arbitrary shell script. So every Codex read asks by default; an exact
`shell` allow rule can automate specific commands.

## Security boundary

- **What Switchyard mediates:** every shell command and every patch Codex runs (verified), with the
  tools listed under "Hardening flags" disabled.
- **What Codex's sandbox adds:** with `sandbox: "workspace-write"`, commands that run *inside* the
  sandbox can write only to the workspace (and temp directories) and have no network. Verified:
  `curl` failed inside the sandbox even after approval.
- **What it does not add (verified):** under `untrusted`, an **approved** command or patch can run
  outside the sandbox. An approved `touch` and an approved patch both wrote to `/Users/Shared`, outside
  the workspace and outside temp directories. So an approval is as strong as it is for Claude: the
  operation runs with the user's privileges.
- **Not mediated:** what the model sends to OpenAI (file contents it has read become part of the
  conversation); and sub-agent spawning (`collabAgentToolCall`), which cannot be disabled in 0.166.0.
  Sub-agents' own commands are still routed as approval requests, and Switchyard denies them.
- Switchyard does not weaken Codex's defaults: it never uses `danger-full-access`, `never` or
  `acceptForSession`, never sets `externalSandbox`, and never answers with a policy amendment.
- Policies and worktrees are not an OS-level sandbox, for Codex as for Claude.

## Capability differences

| Capability | Claude Code | Codex |
|---|---|---|
| Multi-turn sessions | supported | supported |
| Streaming text | supported | supported |
| Tool activity | supported | supported |
| Permission requests to Switchyard | supported (per tool use) | supported (per command or patch) |
| Denial reason delivered to the agent | supported | unsupported (Codex only says "rejected") |
| Interrupt a turn | supported | supported |
| Queue a message for the next turn | supported (by the CLI) | supported (by the adapter) |
| Change a running turn | unsupported | unknown (Codex has `turn/steer`; not used or tested) |
| Resume a finished session | supported | supported |
| Switchyard-assigned native id | supported | unsupported (Codex assigns the thread id) |
| Token usage | unknown (reported by Claude, not surfaced) | supported |
| Cost | supported | unsupported (Codex reports tokens, not cost) |
| File reads as a distinct tool | supported | unsupported (reads are shell commands) |

## Known limitations

- `app-server` is marked experimental by the CLI; a new Codex release may change the protocol. The
  adapter is verified against 0.166.0 only.
- Every Codex read is a shell command and asks by default.
- Patches mixing additions, edits and deletions, and file moves, are denied; Codex has to split them.
- Sub-agents are denied, not supported.
- The denial reason is not shown to the model.
- No cost reporting.
